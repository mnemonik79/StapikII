# STRATEGY.md

## Цель проекта

Модернизировать устаревший скрипт `legacy_process_order.php` в современный безопасный backend-сервис с использованием практик, изученных в курсе:
- архитектурное разделение ответственности;
- безопасная работа с данными;
- тестирование;
- документация;
- осознанное применение AI.

---

## 1. Анализ исходного legacy-решения

Исходный скрипт содержал ряд типичных проблем legacy-кода:

- смешение логики HTTP, бизнес-логики и работы с БД в одном файле;
- отсутствие валидации входных данных;
- прямую подстановку значений в SQL-запросы;
- отсутствие проверки существования товаров;
- отсутствие обработки ошибок;
- отсутствие тестов;
- отсутствие документации;
- отсутствие авторизации и проверки прав доступа.

Такой код может работать как прототип, но не соответствует требованиям production-решения.

---

## 2. Выбранный стек

Для реализации был выбран стек **Python + FastAPI**.

### Почему FastAPI:
1. Позволяет быстро создавать REST API.
2. Имеет встроенную валидацию через Pydantic.
3. Поддерживает type hints.
4. Автоматически генерирует OpenAPI/Swagger документацию.
5. Хорошо подходит для тестирования.
6. Удобен для разделения проекта на router/service/repository.

### Дополнительные технологии:
- **Pydantic** — валидация запросов и ответов;
- **SQLAlchemy** — безопасная работа с БД;
- **Pytest** — тестирование;
- **Uvicorn** — запуск приложения.

---

## 3. Архитектурная стратегия

Выбрана архитектура:

**routers → services → repositories**

### Причины выбора:
- упрощает поддержку проекта;
- позволяет изолировать бизнес-логику;
- делает код тестируемым;
- уменьшает связанность компонентов;
- соответствует требованиям задания.

### Принципы:
- **тонкий роутер** — только принимает/возвращает данные;
- **толстый сервис** — содержит бизнес-логику;
- **репозиторий** — изолирует слой доступа к БД.

---

## 4. Подход к безопасности

Безопасность была включена в проект как обязательный слой, а не как дополнительная опция.

### Реализованные меры:
1. **Безопасная работа с БД**
   - исключена ручная подстановка SQL;
   - используется ORM / параметризованные запросы.

2. **Валидация входных данных**
   - `user_id` должен быть положительным числом;
   - `items` должен быть непустым списком;
   - каждый item содержит `id` и `qty`;
   - `qty > 0`.

3. **Проверка прав доступа**
   - пользователь может создавать заказ только от своего имени.

4. **Обработка ошибок**
   - ошибки переводятся в корректные HTTP-статусы;
   - внутренние детали не раскрываются клиенту.

5. **Защита от утечек**
   - в логах и ответах не должны появляться секреты, токены, SQL-трейсы и чувствительные данные.

## 8. Стратегия использования AI

В проекте использован **гибридный подход** к применению искусственного интеллекта.

### AI использовался для:
- анализа legacy-кода;
- генерации идей по рефакторингу;
- подготовки структуры проекта;
- генерации тестовых сценариев;
- подготовки черновиков документации;
- формулирования требований к безопасности и качеству.

### Человек оставил за собой:
- финальное архитектурное решение;
- проверку бизнес-логики;
- проверку корректности библиотек и API;
- проверку безопасности;
- финальное ревью кода;
- принятие итоговых решений.

---

## 9. Почему выбран гибридный подход

Полностью полагаться на AI при разработке backend-сервиса рискованно, потому что модель может:
- галлюцинировать несуществующие библиотеки и методы;
- предлагать небезопасные решения;
- ошибаться в деталях бизнес-логики;
- пропускать edge cases.

Поэтому был выбран **гибридный режим**:

- AI ускоряет рутинные задачи;
- человек контролирует критические решения.

Этот подход даёт лучший баланс между скоростью и качеством.

## 10. Как контролировалось качество AI-результатов

Для безопасного использования AI применялись следующие практики:

1. Проверка всех библиотек и API по документации.
2. Проверка отсутствия галлюцинаций.
3. Ручной review архитектуры.
4. Проверка безопасности входных данных и запросов.
5. Запуск тестов на позитивные, негативные и граничные сценарии.
6. Ручная проверка итоговой бизнес-логики.

---

## 11. Обоснование стратегии использования AI: облако / локально / гибрид

Для проекта выбран **гибридный подход**.

### Почему не только облако:
- есть риск передачи чувствительного кода или данных во внешний сервис.

### Почему не только локально:
- локальные модели могут уступать по качеству генерации и анализа.

### Почему гибрид:
- общие задачи, шаблоны, документация и идеи можно решать с помощью внешнего AI;
- чувствительные детали, финальная валидация и проверка безопасности остаются под контролем разработчика.
